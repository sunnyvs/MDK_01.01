## 28. Ломай специально

### Главная мысль

Проверять программу на том вводе, для которого ты её писал, почти бесполезно: она для него и написана. Баги живут **на краях** — там, где данных нет, где их слишком много, где пользователь ввёл не то.

Поэтому правило одно: **после «заработало» попробуй сломать.** Времени это занимает пару минут, а находит то, что иначе всплывёт при сдаче работы.

### Восемь входов, которые стоит прогнать всегда

| Что подать | Что проверяет | Как обычно ломается |
|---|---|---|
| буква вместо числа (`abc`) | защиту чтения | поток ломается, дальше всё нули |
| просто Enter, пустая строка | пустой ввод | имя пустое, в таблице дыра |
| `0` | деление, пустые списки | падение или `nan` |
| `-5` | отрицательные | `while (n > 0)` не выполнится ни разу |
| `2000000000` | переполнение | молча отрицательный результат |
| очень большое (`99999999999999999999`) | переполнение при **чтении** | в переменной окажется `INT_MAX` |
| границы диапазона (ждёшь 1–8 → дай 0, 1, 8, 9) | `<` против `<=` | лишний или недостающий виток |
| **обрыв ввода** (`Ctrl+Z`, затем Enter) | конец потока | **бесконечный цикл** |

Последняя строка — самая недооценённая. Пока вводишь руками, ввод не кончается никогда, и кажется, что проверять нечего. Но именно на ней зависает наивная функция чтения: `>>` проваливается, `clear()` честно снимает флаг, читать нечего — и программа вечно печатает «Нужно число». Разбор — в [разделе 4](02-vvod-vyvod.md#безопасное-чтение--держи-под-рукой).

## Подавать ввод из файла, а не руками

Прогонять восемь случаев руками — скучно, и на третий раз начинаешь халтурить. Проще один раз сложить ввод в файл и скармливать его программе.

Создай `test1.txt`:

```
abc
-5
0
```

Дальше — внимание, **в PowerShell не работает привычный способ**:

```powershell
.\main.exe < test1.txt      # ❌ The '<' operator is reserved for future use
```

Это особенность PowerShell, а не ошибка в программе. Рабочий вариант:

```powershell
Get-Content test1.txt | .\main.exe
```

А если открыт терминал MSYS2 (bash), там работает классическая запись:

```bash
./main.exe < test1.txt
```

Проверено на твоём окружении: способ с `Get-Content` отрабатывает и корректно доводит программу до конца ввода — то есть **заодно проверяет тот самый обрыв ввода**, о котором сказано выше. Один запуск закрывает сразу два пункта таблицы.

Держи два-три таких файла рядом с программой (`test_ok.txt`, `test_bad.txt`) — и проверка каждой новой версии займёт секунды.

## Живой пример: как нашёлся `-nan%`

Это не выдуманная история — так был найден баг в [Расходах из файла](../examples/05-raskhody-csv.md).

Программа читает файл с расходами и печатает долю каждой категории. На обычных данных всё верно:

```
еда                750.75       3    42.4%
транспорт          120.00       2     6.8%
```

Дальше по методу выше: «а что, если суммы нулевые?». Файл из двух строк с нулями:

```
2026-09-01;еда;0
2026-09-02;транспорт;0
```

Результат:

```
еда                  0.00       1    -nan%
транспорт            0.00       1    -nan%
```

Причина простая: доля считается как `100.0 * sum / total`, а `total` оказался нулём. Деление нуля на ноль даёт `nan` — и оно не падает, а тихо просачивается в вывод.

Самое интересное: справочник **предупреждает** об этой ловушке в [разделе 5](03-logika-cikly.md#ловушка-4-деление-на-ноль), а программа всё равно на неё наступила. Потому что рассуждение было такое: «записи в файле есть, значит `total` не ноль». Записи-то есть, а сумма — ноль.

> **Вывод, который стоит запомнить:** проверяй сам делитель, а не рассуждай о том, откуда он взялся. `if (total > 0)` — одна строка, а рассуждение может оказаться неверным.

Тем же способом нашлись ещё три: имя с `;` тихо портило файл данных, `0` в отрицательной степени давал `inf`, пустое имя оставляло в таблице безымянную строку.

## Программа собралась, но считает не то

Компилятор молчит — значит, дело в логике. Тут помогают три инструмента, в таком порядке:

**1. Проверь на самом простом входе.** Не на `12345`, а на `5`. Не на десяти студентах, а на одном. Если на одном неверно — искать проще в десять раз.

**2. Напечатай промежуточные значения.** Грубо, зато сразу видно:

```cpp
std::cout << "dx = " << dx << ", dy = " << dy << "\n";   // потом удалить
```

Печать хороша, когда нужно проследить **историю**: как менялось значение за все двести витков цикла.

**3. Открой отладчик.** [Точка останова и панель Variables](01-osnovy.md#отладчик-увидеть-что-происходит-внутри) показывают все переменные сразу, ничего не добавляя в код. Отладчик выигрывает, когда непонятно, **где** именно ломается.

### Как сузить область поиска

Если непонятно, в каком месте программа сходит с рельсов, работает деление пополам:

1. Поставь точку останова примерно посередине программы.
2. Дошло досюда правильно? Значит, ошибка ниже. Неправильно — выше.
3. Повтори с той половиной, где ошибка.

За четыре-пять шагов так локализуется любая ошибка в файле на пятьсот строк. Тот же приём, что в игре «угадай число» — и работает по той же причине.

## Три флага, которые ищут баги за тебя

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion -D_GLIBCXX_ASSERTIONS -g -O0 -o main.exe main.cpp
```

| Флаг | Что находит |
|---|---|
| `-Wall -Wextra` | неинициализированные переменные, `=` вместо `==`, потерянный `return` |
| `-Wconversion -Wsign-conversion` | незаметную потерю точности и знака |
| `-D_GLIBCXX_ASSERTIONS` | **выход за границы** `vector` и `string` во время работы |

Первые два ловят ошибки до запуска, третий — во время. Все три уже прописаны в твоём `settings.json`, так что `Ctrl+Alt+R` собирает с ними. Подробности — [раздел 1](01-osnovy.md#сборка).

> Помни про [ловушку с `is_open()`](08-struct-fayly.md#сначала--главная-ловушка-на-твоей-сборке): проверка открытия файла через `if (!in)` на этой сборке **молча пропускает** отсутствующий файл. Никакие флаги этого не поймают — только правильная проверка.

## `assert`: проверка невозможного

Флаги ловят типовые ошибки, а `assert` из `<cassert>` ловит **твои личные предположения**. Ставишь его туда, где что-то «не может быть», — и если однажды оно случится, программа остановится ровно на этой строке с понятным сообщением, а не досчитает молча до чепухи.

```cpp
#include <cassert>
#include <iostream>
#include <vector>

double average(const std::vector<int> &v) {
  assert(!v.empty() && "average() вызвана с пустым вектором");   // условие, которого «не должно быть»
  int sum = 0;
  for (int x : v)
    sum += x;
  return static_cast<double>(sum) / static_cast<double>(v.size());
}

int main() {
  std::vector<int> data = {4, 6, 8};
  std::cout << average(data) << "\n";   // → 6
  return 0;
}
```

Приём `assert(условие && "текст")` — стандартная идиома: строка ни на что не влияет при истинном условии, но попадает в сообщение, если проверка сорвалась. Два правила:

- `assert` — для того, что **обязано** быть верным по логике программы (непустой вектор, индекс в границах), а **не** для проверки пользовательского ввода: ввод проверяют обычным `if` и вежливым сообщением, а не падением.
- В «боевой» сборке с флагом `-DNDEBUG` все `assert` выключаются и ничего не стоят. Поэтому внутри `assert(...)` не должно быть кода с побочными эффектами (`assert(v.pop_back(), ...)` — так нельзя): в релизе он просто не выполнится.

## Чеклист: две минуты перед сдачей

- [ ] Собрал с `-Wall -Wextra` — предупреждений **ноль**
- [ ] Прогнал восемь входов из таблицы выше
- [ ] Обрыв ввода (`Ctrl+Z`) не вешает программу
- [ ] Пустые данные не дают `nan` и не роняют программу
- [ ] Каждый делитель проверен на ноль, каждый контейнер — на пустоту
- [ ] Обращений к `v[i]` за границей нет
- [ ] Файлы проверяются через `is_open()`
