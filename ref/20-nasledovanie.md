## 35. Наследование

> 📖 **Определение.** **Наследование** — когда один класс (**производный**) берёт поля и методы другого (**базового**) и достраивает своё. **Полиморфизм** — вызов одного и того же метода делает разное в зависимости от реального типа объекта. Термины — в [словаре](10-slovar.md#про-классы-ооп).

### Идея: «является частным случаем»

Наследование — способ сказать «тип **B** — это частный случай типа **A**». Круг — это фигура; собака — это животное; кнопка — это виджет. Наследник получает поля и методы базового типа и **добавляет своё**.

```cpp
class Shape {                    // база: общее для всех фигур
 public:
  double perimeter = 0;
};

class Circle : public Shape {    // «Circle — это Shape»
 public:                         // Circle получает perimeter от Shape и добавляет radius
  double radius = 0;
};

Circle c;
c.radius = 2;
c.perimeter = 12;                // поле, унаследованное от Shape
```

`class Circle : public Shape` читается «Circle публично наследует Shape». `public` здесь — это про отношение «является»; оно почти всегда и нужно.

### `protected` — видно наследникам

К `private`-полям базы наследник **не** имеет доступа — они спрятаны даже от него. Если поле должно быть закрыто снаружи, но доступно наследникам, его помечают `protected`:

```cpp
class Shape {
 protected:
  std::string name;      // видно самому Shape и его наследникам, но не снаружи
};

class Circle : public Shape {
 public:
  void setup() { name = "круг"; }   // ✅ наследник видит protected-поле базы
};

Circle c;
c.name = "x";            // ❌ снаружи protected недоступно, как и private
```

### Конструктор наследника вызывает базовый

При создании наследника сначала строится базовая часть. Её конструктор зовут в списке инициализации — первым:

```cpp
class Shape {
 public:
  Shape(std::string n) : name(n) {}
 protected:
  std::string name;
};

class Circle : public Shape {
 public:
  Circle(double r) : Shape("круг"), radius(r) {}   // сначала база Shape, потом своё поле
 private:
  double radius;
};
```

### Виртуальные методы: вызвать нужную версию

Вот ради чего всё затевалось. Пометь метод базы словом `virtual` — и наследник может дать **свою** версию (`override`). Тогда вызов через **указатель или ссылку на базу** попадёт в версию настоящего типа объекта. Это называется **полиморфизм**.

```cpp
class Shape {
 public:
  virtual double area() const { return 0; }   // virtual: наследник может переопределить
};

class Circle : public Shape {
 public:
  Circle(double r) : radius(r) {}
  double area() const override {               // override: своя площадь вместо базовой
    return 3.14159 * radius * radius;
  }
 private:
  double radius = 0;
};

Circle circle(2.0);
Shape &s = circle;             // ссылка на базу, а объект — Circle
std::cout << s.area();         // → 12.5664   вызвалась Circle::area, а не Shape::area
```

Без `virtual` вызвался бы `Shape::area` (по типу ссылки), и полиморфизм бы не работал. Слово **`override`** не обязательно, но пиши его всегда: если сигнатура случайно разойдётся с базовой (`aera` вместо `area`, забытый `const`), компилятор поймает это сразу, а не оставит молчаливый баг.

Пустая базовая версия часто бессмысленна («площадь фигуры вообще» — чего?). Тогда метод делают **чисто виртуальным** (`= 0`): база превращается в **абстрактную** — её нельзя создать, только наследовать.

```cpp
class Shape {
 public:
  virtual double area() const = 0;   // чисто виртуальный: у «просто фигуры» площади нет
};
Shape s;                             // ❌ error: нельзя создать абстрактный класс
```

### Виртуальный деструктор — обязателен

Как только у класса есть хоть один `virtual`-метод и его наследуют через указатель на базу, **деструктор базы обязан быть виртуальным**:

```cpp
class Shape {
 public:
  virtual double area() const = 0;
  virtual ~Shape() = default;        // ✅ без этого — беда при удалении через Shape*
};
```

Почему: `delete basePtr` без виртуального деструктора вызовет только `~Shape()`, а `~Circle()` — нет. Ресурсы, которые держал `Circle`, **утекут**, и это [неопределённое поведение](10-slovar.md). С умными указателями ([раздел 33](18-umnye-ukazateli.md)) правило то же: `unique_ptr<Shape>` корректно удалит `Circle` только при виртуальном деструкторе. Правило простое: **есть `virtual`-метод — есть и `virtual`-деструктор.**

### Вызвать базовую версию: `Base::method()`

Переопределяя метод, часто хочется не заменить базовую версию целиком, а **дополнить** её: сделать общую часть базы, а потом добавить своё. Базовую версию зовут по имени класса — `Base::method()`:

```cpp
#include <iostream>

class Enemy {
 public:
  virtual void describe() const {
    std::cout << "враг, hp=" << hp_ << "\n";
  }
  virtual ~Enemy() = default;

 protected:
  int hp_ = 100;
};

class Boss : public Enemy {
 public:
  void describe() const override {
    Enemy::describe();                              // сначала — общая часть базы
    std::cout << "  БОСС, фаза " << phase_ << "\n"; // потом — своё дополнение
  }

 private:
  int phase_ = 1;
};

int main() {
  Boss b;
  b.describe();
  // → враг, hp=100
  //     БОСС, фаза 1
  return 0;
}
```

Без явного `Enemy::` обычный вызов `describe()` внутри метода `Boss` попал бы в **себя же** и зациклился — поэтому базовую версию всегда указывают полным именем. Приём «сначала базовая версия, потом своё дополнение» встречается постоянно: общее поведение живёт в базе и не дублируется, а наследник лишь достраивает частности.

> Родственное ключевое слово — `final`: `void describe() const override final;` запрещает переопределять метод дальше, а `class Boss final : public Enemy` запрещает наследовать сам класс. Ставят, когда хотят зафиксировать конец иерархии.

### Пример целиком: фигуры

Всё вместе — список **разных** фигур через общий базовый тип, и каждая считает свою площадь сама:

```cpp
#include <iostream>
#include <memory>
#include <vector>

class Shape {
 public:
  virtual double area() const = 0;     // у каждой фигуры своя площадь
  virtual ~Shape() = default;          // виртуальный деструктор — обязателен
};

class Circle : public Shape {
 public:
  Circle(double r) : radius(r) {}
  double area() const override { return 3.14159 * radius * radius; }
 private:
  double radius;
};

class Rectangle : public Shape {
 public:
  Rectangle(double w, double h) : width(w), height(h) {}
  double area() const override { return width * height; }
 private:
  double width;
  double height;
};

int main() {
  std::vector<std::unique_ptr<Shape>> shapes;      // разные фигуры в одном списке
  shapes.push_back(std::make_unique<Circle>(2.0));
  shapes.push_back(std::make_unique<Rectangle>(3.0, 4.0));

  for (const auto &shape : shapes)
    std::cout << shape->area() << "\n";   // → 12.5664  и  12  — у каждой своя версия area()
  return 0;
}
```

Один цикл, один вызов `shape->area()` — а выполняется то `Circle::area`, то `Rectangle::area`, смотря что за объект. Добавить новую фигуру — значит просто написать ещё один класс-наследник; цикл трогать не нужно. В этом сила полиморфизма.

### Наследование или композиция

Наследованием часто злоупотребляют. Прежде чем наследовать, проверь отношение:

| Наследование — «**является**» | Композиция — «**содержит**» |
|---|---|
| `Circle` **является** `Shape` | `Car` **содержит** `Engine` (поле, а не база) |
| нужен полиморфизм: разные типы через общий | просто собрать объект из частей |
| `class Circle : public Shape` | `class Car { Engine engine; … };` |

Если тянет написать «A наследует B», но по смыслу A **содержит** B или **использует** B — бери поле (композицию), а не наследование. Наследование оправдано, когда есть настоящее «является» **и** нужен полиморфизм через базовый тип.

### Типовые ошибки

```cpp
// 1. Забыл virtual → вызвалась базовая версия, полиморфизм не работает
class Shape { public: double area() const { return 0; } };        // ❌ не virtual
Shape *s = new Circle(2.0);
s->area();                        // → 0   вызвался Shape::area, не Circle::area

// 2. Забыл virtual-деструктор → утечка при удалении через базовый указатель
class Shape { public: virtual double area() const = 0; };         // ❌ нет ~Shape() virtual
// delete базового указателя не позовёт деструктор наследника

// 3. Срезка (slicing): хранишь наследника в базе ПО ЗНАЧЕНИЮ — «наследная» часть теряется
Circle c(2.0);
Shape base = c;                   // ❌ в base влезла только Shape-часть, radius потерян
                                  //    поэтому полиморфизм — через указатель/ссылку, не по значению
```

> Наследование — мощный, но не первый инструмент. В учебных задачах чаще выручают `struct`, `vector` и свободные функции. Берись за него, когда появляется **семейство типов с общим поведением**, которое надо перебирать единообразно, — и тогда обязательно `virtual`-методы, `override` и `virtual`-деструктор.
